## 1. 产品是什么、服务谁、暂时不做什么

### 一句话定义

小奶瓶是一款给 0–3 岁宝宝照护者使用的 iOS 原生成长记录 App。它的核心不是医疗监控，而是以低负担的高频记录，把喂养、睡眠、排便、喝水、照片、成长指标、疫苗与纪念日沉淀成一份温柔、可信任、有纪念册感的个人档案。

### 核心用户与关键场景

核心用户是新手妈妈；也应允许爸爸、祖辈等照护者使用，但第一版不做多人协作。典型场景是：

- 半夜、刚醒、单手、注意力被宝宝占用时，快速记一顿奶、一次睡眠或一次换尿布；
- 白天随手补一条喝水、照片、身高体重或纪念日；
- 看“今天已经记了什么”“距上次喂养多久”“下一次要不要提醒”；
- 月末回看成长记录；
- 换机后恢复用户主动录入的记录和主动加入 App 的照片。

### 明确范围

第一版是 iOS-only、单人记录、免费验证、离线优先。已经实现或已进入范围的能力包括：档案、今日概览、喂养、喝水、睡眠、排便、相册、成长曲线、疫苗记录、纪念日、月报、通知、账号与同步、照片原图同步、账号删除、Widget / Live Activity 的最小路径。

明确不做：Android、Web、macOS、家庭成员协作、公开分享/社区、广告、电商、订阅、付费墙、健康诊断、育儿医疗建议、第三方分析 SDK、复杂可查看用户内容的运营后台。

### 成功标准

产品目标不是“功能多”，而是让真实家庭愿意连续使用。已有规格将成功焦点表述为：降低每次记录的操作负担，提升 30 天持续记录意愿；首页应让用户在 1–2 步内完成高频记录。

## 2. 体验与视觉语言

### 情绪和风格

视觉关键词是：温柔、干净、低负担、私人纪念册、可信任。界面用奶白纸张纹理作背景，配浅粉、雾蓝、草绿卡片，水彩宝宝/奶瓶/云朵插画，深绿正文与珊瑚色重点数字。它刻意避免：医院仪表盘、红色预警、社交动态流、广告感和过度儿童化。

### 设计系统

- `AppColors`：奶白、暖粉、雾蓝、草绿、珊瑚、墨绿等。
- `AppTypography`：品牌字形用于标题、按钮和数字；密集表单与系统控件保留可读的系统回退。
- `WatercolorCard`：全 App 摘要和操作卡片的统一容器。
- `PrimaryWatercolorButton`：明确、高频的主操作。
- `ScreenScaffold`：统一纸张背景、页面标题、返回和顶部辅助动作。
- `LiquidGlassTabBar`：四个主 Tab 的底部玻璃感导航。

### 可用性规则

高频按钮最小点击区域应不小于 44pt；表单默认当前时间，核心必填字段不超过两个；详情字段逐步展开；保存失败不丢失输入；空状态要给下一步；删除使用破坏性样式并二次确认。夜间模式和“安静育儿模式”都已经在设置页出现，其中安静育儿模式默认开启，用于避免 App 内白噪音误播放。

## 3. 当前信息架构与导航

### 实际 App 的四个主 Tab

| Tab | 当前职责 | 主要内容 |
|---|---|---|
| 今天 | 当天状态和快捷入口 | 宝宝出生天数、今日记录卡片、最近记录、纪念日/疫苗摘要、白噪音 |
| 成长 | 长期指标和健康记录管理 | 身高体重曲线、三项最新指标、疫苗本、月度报告 |
| 记录 | 汇集所有录入入口 | 喂养、喝水、睡眠、排便、照片、身高体重、纪念日，以及今日概览、最近记录 |
| 设置 | 档案、同步和偏好 | 头像/宝宝信息、疫苗本、账号同步、数据隐私、安静模式、夜间模式、Live Activity |

> 注意：早期 UI 契约曾写成“今天 / 时间线 / 成长 / 设置”，而当前实际实现是“今天 / 成长 / 记录 / 设置”。相册目前是从首页或记录入口进入的二级页面，不是主 Tab。这是现行信息架构与旧文档的一处差异。

### 首次使用

1. 首次启动展示三页水彩欢迎引导。
2. “开始记录”进入创建宝宝档案；前两页“先看看”切换引导页，最后一页进入无档案的主页面预览。
3. 建档填写昵称、出生日期、性别等最小信息。
4. 建档后进入四 Tab 主界面。
5. 登录不是建档的前置阻断；用户可先本地记录，后在设置中登录并同步。

### 当前全局记录入口

目前并不存在真正悬浮、随页面可用的单一“全局 +”按钮。底部第三项“记录”是一个 Tab，进入后看到七个大卡片入口；今天首页另有五个高频卡片入口。这意味着同一个“记录”概念有两层：

- 首页：看状态后，点击具体卡片记录；
- 记录 Tab：先进入记录中心，再选择类型；
- 具体业务页：再点击页面底部/空状态里的“+ 记录…”进入表单。

其优点是类型清晰、改动少；缺点是高频场景可能多一次选择或滚动，尤其是“进入喂养页后仍需要再找 + 记录喂养”。这是本轮讨论的重点。

## 4. 页面与功能逐页说明

### 4.1 今天首页

**目的**：让用户一眼知道今天的照护状态，并从这里直接进入高频记录。

**页面结构**：

1. 顶部：宝宝头像、昵称、疫苗/提醒入口。
2. Hero：`宝宝今天第 N 天`，配奶瓶、云朵、小熊插画。
3. 今日记录网格：记喂养、记喝水、睡眠记录、记排便、加照片。
4. 最近记录：按发生时间倒序，展示时间、类型、关键值。
5. 两张提示卡：自动纪念日和下一针疫苗。
6. 睡前小声音：柔雨等白噪音选择、音量控制；安静育儿模式开启时禁用播放。

**数据**：首页从本地 `BabyRecordStore` 实时汇总今天的记录。喂养显示次数、总奶量与距上次时间；喝水显示次数/毫升；睡眠显示累计或进行中；排便显示次数；照片显示张数。

**已知观察点**：截图中“记喝水”已使用明确蓝色水滴；排便仍使用排便专属插画。最近记录同样会以水滴区分喝水。

### 4.2 喂养记录

**目的**：管理喂养历史、补录/编辑一顿奶，以及管理本机喝奶提醒。

**当前结构（见截图 02）**：

1. 顶部四指标：今日喂养次数、总奶量、最近一次时间、距上次。
2. 中部整块“喝奶闹钟”：下一次提醒状态、日期选择、时间选择、提醒模式（只一次/2/2.5/3/3.5/4 小时）、保存或取消按钮。
3. 下方喂养历史：时间、类型、奶量或时长、距上次；右侧每条记录有删除按钮。
4. 页面较下方的“+ 记录喂养”进入新增表单。
5. 顶部“统计”进入月度/聚合查看路径。

**新增/编辑表单**：可填写发生时间、喂养类型（母乳、瓶喂/奶粉等）、奶量或时长、备注等；保存后本地数据更新，首页和月报随之重算。编辑态可保存修改或取消；删除有二次确认。

**现行提醒规则（重要）**：

- 当前规格和代码的基线是**用户手动设置一个本机下一次喝奶闹钟**，不是自动按上一顿计算。
- 用户可以选择只提醒一次，或按 2–4 小时固定间隔继续提醒。
- 提醒在触发前 5 分钟通知；系统通知拒绝时，提醒时间仍可保留并显示相应提示。
- 提醒不随云端同步；换档案、清空本地数据或恢复云端数据时清理旧提醒。
- 已有固定间隔时，保存新喂养可以手动将下一次提醒顺延 0–30 分钟。
- 可选 Live Activity/灵动岛用于显示下一次提醒和固定间隔；不是历史记录编辑界面。

**本轮反馈对应的体验问题**：页面主视觉目前是闹钟而不是“记一顿奶”。全日期按钮还显示年份；历史行的删除视觉权重较高；“+ 记录喂养”在用户看完闹钟和列表之后才出现。因此新用户会误认为中部闹钟是必经步骤。

### 4.3 喝水记录

**目的**：独立记录饮水，且不影响喝奶闹钟计算。

**流程**：从首页或记录 Tab 点击“喝水” → 默认当前时间、60ml → 以 10ml 为步长调节，范围 10–600ml → 保存 → 当天列表显示时间和毫升，可删除。

**边界**：喝水写入本地并可随账号同步；不参与喂养统计、喂养间隔或喝奶提醒。这一功能属于 2026-07 的体验补充。

### 4.4 睡眠记录

**目的**：记录开始、结束和补记睡眠，不把进行中睡眠与已结束累计混为一谈。

**页面能力**：显示今日已结束睡眠时长；若睡眠进行中，则显示开始时间并提供结束/补记；列表按时段显示；支持新增、编辑、删除；空状态有“开始睡觉”和“补记”。表单可填写开始、结束、类型和可选备注，并校验时间顺序。

### 4.5 排便记录

**目的**：快速记一次换尿布/大小便，并按需保留观察细节。

**页面能力**：今日大便、小便、最近一次摘要；列表；“+ 记录一次”；新增/编辑；删除确认。表单核心记录是发生时间和类型；颜色、形态、备注是“更多详情（可不填）”，避免把每次换尿布变成繁琐的医疗表单。该功能是记录工具，不应输出医学判断。

### 4.6 相册与照片详情

**目的**：把用户主动加入 App 的照片变成成长时间线。

**入口和操作**：从首页“加照片”或记录 Tab“照片”进入。支持系统相册选择和相机拍照；选定后复制到 App 私有空间，而不是扫描或自动上传系统相册。可编辑照片日期、备注、封面/展示；可删除，并有确认。页面显示总照片数和本月照片，空状态解释“不会自动上传”。

**隐私边界**：只有用户主动加入的照片才进入 App；登录并启用同步后，原图可上传到私有对象存储，以便恢复。当前不上传缩略图。删除照片要同时处理本地文件、元数据和云端对象；失败时需可重试。

### 4.7 成长、疫苗与月报

**成长页**：顶部为体重/身高/头围三段选择和折线图；中部展示最近一次体重、身高、头围；支持新增、编辑、删除成长记录，至少应有一项身高或体重；可跳转完整月报和疫苗本。

**疫苗本**：支持中国大陆和香港模板；模板按生日生成可编辑计划记录；记录可标记计划、已预约、已接种，填写日期和备注，支持新增、编辑、删除。App 明确提示：模板仅用于记录和提醒，实际安排以医生/接种机构为准，不提供医疗建议。

**月度报告**：基于本地原始记录即时聚合，不把月报作为必须同步的独立重数据。聚合喂养、喝水、睡眠、排便、照片、成长指标、纪念日、疫苗未完成项等。记录不足时显示温和空状态，不补造数据。

### 4.8 纪念日

自动纪念节点根据出生天数计算（如满月、百天）；用户可另加手动纪念日，填写日期和可选详情，支持编辑/删除。删除手动纪念日不会改变宝宝档案。首页展示最近的自动纪念提示。

### 4.9 设置、档案与账号同步

**档案**：修改宝宝昵称、出生日期、性别和头像。头像来自用户主动选择的照片，支持裁剪/缩放/旋转。

**模式与设备体验**：

- 安静育儿模式：默认开，防止 App 内白噪音在夜间误响；
- 夜间模式：设置页开关，切换为低亮度深色界面；
- 灵动岛喝奶提醒：可开关，另有 3 分钟临时提醒的测试入口。

**账号路径**：设置中显示“登录并自动同步”。配置可用时支持手机号验证码与微信登录。登录后自动尝试同步；退出只清除本设备会话，不删除账号数据；删除云端账号会删除云端同步记录、照片原图及可识别分析事件，并清理本地档案/记录/照片（需二次确认）。

## 5. 本次最值得让 GPT 讨论的产品决策

### 决策 A：喂养页到底是“记录页”还是“闹钟页”？

**当前事实**：进入喂养页后的第一大块是闹钟设置；新增记录按钮在列表后方。

**用户意图**：用户说“点进来就是要记录的”“我每次都点成中间那个”。这说明用户心智模型是：喂养页首先是记录入口，提醒应是记录后的附属结果。

**推荐讨论方案**：

| 方案 | 做法 | 优点 | 风险/代价 |
|---|---|---|---|
| A（推荐）记录优先、提醒收纳 | 顶部固定“记录喂养”；保存后自动建下一次提醒；闹钟缩成一行状态，点开才编辑 | 最贴合单手高频任务；减少一层认知 | 需定义默认提醒间隔和关闭策略 |
| B 保留手动闹钟但移到底部 | 记录按钮移顶部，原闹钟仍存在但折叠在历史后 | 改动小 | 仍要求用户理解两套操作 |
| C 拆成两个独立页面 | 喂养历史/记录页与提醒设置页完全分开 | 概念最清晰 | 多一次导航，可能不适合半夜场景 |

**如果采用“保存即自动提醒”，必须先定的规则**：默认是 3 小时还是沿用上一次用户选择？是否每一顿都自动覆盖旧提醒？用户何时可关闭自动提醒？是否允许“这次不提醒”？跨午夜时如何显示？通知未授权时只保存计划、还是提示并引导授权？这些都是产品规则，不能只改 UI。

### 决策 B：日期是否显示年份？

**当前事实**：提醒日期使用 DatePicker，屏幕上显示完整 `2026年7月25日`。底层完整日期必须保留，跨年/跨月提醒才可靠。

**推荐视觉格式**：

- 当天：`今天`；
- 次日：`明天`；
- 同一年其他日期：`7月25日`；
- 跨年：`2027年1月3日`。

这样减少阅读噪音，不改变日期选择、持久化或通知正确性。需要注意：只隐藏年份不是让日期控件失去选择年份的能力；编辑态仍要允许用户选择未来跨年日期。

### 决策 C：是否做真正的全局记录按钮？

**当前事实**：底部“记录”是一个 Tab，不是立即创建操作；首页与记录中心重复提供入口。

**可讨论的三种模式**：

1. 保留“记录”Tab（当前）：信息组织清楚，但从记录中心到表单通常需要两次点击。
2. 中间 Tab 改为“+”按钮：点击立即弹出底部 Sheet，先选喂养/喝水/睡眠/排便/照片；长按或次级入口才看记录中心。这是高频产品最直接的模式。
3. 所有主页面右下角浮动“+”：随时可录入，但可能遮挡底部 Tab、列表删除或系统手势，视觉上更像工具型 App。

**当前建议**：先验证“中间 Tab 点开立即出现类型选择”的轻量方案，不急于引入全局悬浮按钮。它保留用户已认识的“记录”标签，也满足“点一下就开始记录”。

### 决策 D：记录列表的删除与二次操作

截图中每条喂养记录右侧有显眼垃圾桶，行里还出现“快速记录”语义。这对需要扫读时间线的用户造成噪声。

可选方向：

- 行点击进入编辑详情；右侧仅保留关键值；删除放入编辑页，或采用 iOS 左滑删除 + 二次确认；
- 如果保留右侧按钮，优先放“编辑”而非“删除”；
- 历史行需要的信息排序应是：时间 → 类型/关键值 → 与上次间隔；“快速记录”不属于历史记录本身，应删除。

### 决策 E：喂养记录自动提醒是否与“照护建议”边界冲突？

自动提醒本身可以是用户主动选择的节奏工具；但 App 不应根据月龄、奶量或医疗知识替用户推荐“该 2 小时/3 小时喂一次”。安全的产品边界是：用户首次自己选择默认间隔，之后 App 只执行用户保存的偏好；任何时间都能关闭、修改或跳过本次提醒。

## 6. 数据模型与业务规则

### 本地优先原则

`BabyRecordStore` 是 App 的本地状态与持久化中枢。用户的新增、编辑、删除先写本地，UI 再从本地派生首页、列表、月报和 Widget 快照；网络不应阻断记录。网络可用且有登录会话时，后台同步控制器尝试上传。同步失败不能阻塞本地查看或继续编辑。

### 主要对象

| 对象 | 关键字段 | 是否敏感 | 同步情况 |
|---|---|---:|---|
| Baby | ID、昵称、出生日期、性别、头像 | 是 | 是 |
| FeedingRecord | ID、宝宝 ID、发生时间、类型、奶量、时长、备注、创建/更新时间、删除/同步状态 | 是 | 是 |
| WaterRecord | ID、宝宝 ID、发生时间、毫升、创建/更新时间、删除/同步状态 | 是 | 是 |
| SleepRecord | ID、开始/结束时间、类型、时长、备注 | 是 | 是 |
| DiaperRecord | ID、发生时间、大小便、颜色、形态、备注 | 是 | 是 |
| GrowthRecord | ID、测量日期、体重、身高、头围、备注 | 是 | 是 |
| VaccineRecord | ID、标题、计划/实际日期、状态、地区、备注 | 高敏感 | 是 |
| Milestone | ID、标题、日期、可选详情 | 是 | 是/按当前同步包包含 |
| BabyPhoto | ID、发生时间、本地文件、备注、同步元数据 | 高敏感 | 元数据和主动加入的原图都同步 |
| FeedingReminder | 下一次提醒时间、固定间隔、通知 ID | 是 | **本机本地，不上传** |

### 删除与冲突

- 单条业务记录可删除；云端启用时删除需要进入同步队列。
- 照片删除要删除 App 私有文件、照片元数据和远端对象；云端删除失败应显示待完成并重试。
- 删除宝宝档案要清理关联记录和照片；账号删除要清理账号、云端同步、照片和可识别埋点。
- 第一版没有多人实时协作；同一对象冲突按较新的 `updatedAt`，删除优先于更新。
- 月报是原始记录的聚合，删除原始记录后报告自然更新。

### 数据迁移

云同步包有 `schemaVersion`。新增可选字段应向后兼容；例如旧同步包没有 `waterRecords` 时恢复为空数组。涉及云端字段改变，需要同步更新数据模型、同步规则和隐私审查文档。

## 7. 通知、Widget 与 Live Activity

### 本地通知

喝奶闹钟基于 iOS 本地通知，最多保留一个下一次提醒。用户设置固定间隔时，按其选择继续。通知权限被拒绝，不应静默失败：App 仍可保存计划时间，但必须明确告诉用户系统不会弹通知。

### Widget

主 App 与 Widget Extension 通过 App Group 共享最小“今日快照”。Widget 只读，不写记录。允许展示：宝宝昵称、出生天数、今日喂养次数/奶量、上次喂养、进行中睡眠、下一次提醒、固定间隔、今日大小便次数。禁止写入：宝宝照片、备注全文、账号凭证、token、对象 key、同步状态。

### Live Activity / 灵动岛

仅用于喝奶提醒进行中状态，显示下一次提醒和固定间隔；不能成为历史记录或编辑入口。设置页可开关；锁屏 UI 应使用系统实时倒计时，不能使用高亮黄色背景。

## 8. 账号、同步与后端

### 账号与客户端接口

客户端 `CloudSyncController` 管理会话、登录、自动同步、照片删除和账号删除；会话 token 存 Keychain。当前客户端对第一方 API 使用的路径包括：

| 路径 | 操作 | 用途 |
|---|---|---|
| `/v1/auth/phone/request-code` | POST | 请求手机验证码 |
| `/v1/auth/phone/verify` | POST | 验证手机号与验证码，换取会话 |
| `/v1/auth/wechat/login` | POST | 使用微信授权码登录 |
| `/v1/sync` | PUT / GET | 上传或恢复 JSON 同步包 |
| `/v1/photos/{id}` | PUT / GET / DELETE | 上传、下载、删除主动加入的照片原图 |
| `/v1/photos` | GET | 列出可恢复照片元数据 |
| `/v1/account` | DELETE | 删除账号与关联云端数据 |
| `/v1/analytics/events` | POST | 第一方白名单行为事件 |

### 后端边界

后端目标是“账号下同步/恢复”，不是内容运营平台。当前有 Python 最小实现、SQLite 本地验证、MySQL 适配、对象存储适配、聚合运维看板和发布/取证脚本。生产目标是独立的华为云中国大陆 ECS、私有 OBS、独立数据库和 HTTPS 反向代理；不得与同机其他服务复用目录、端口、进程或代理站点。

### 2026-07-24 当时状态的准确表述

以下能力已有最小代码或本地验证：手机号/微信会话、同步 JSON、照片原图上传/列出/下载/删除、账号删除、合规分析事件、MySQL 适配、运维聚合看板。

当时尚不得宣称“已完成生产上线”；该提交前结论已由 1.3.4（15）正式发布和 APP 备案完成的当前状态覆盖。

## 9. 隐私、安全、合规和分析

### 为什么是高敏感产品

App 处理儿童相关资料：昵称、出生日期、头像/照片、喂养、睡眠、排便、成长测量、疫苗计划和家庭备注。这些都不应被用于广告、画像、训练、公开分享或人工内容运营。

### 数据收集和存储原则

- 本地优先：本地记录保存在 App 沙盒；主动加入的照片复制到 App 私有空间。
- 云端目的最小化：只为账号同步/恢复；照片原图只在用户主动加入 App 后上传。
- 访问控制：同步和照片接口需要 Bearer token；生产传输必须 HTTPS；私有对象存储不能给长期裸露公共 URL。
- 不使用 HealthKit、定位、通讯录、支付、麦克风；照片、相机、通知仅在用户实际使用相关功能时请求。
- 不接入第三方广告、归因、热力图或分析 SDK。

### 允许的第一方分析

只在已有登录会话中使用自有 API 上报白名单行为事件，例如 App 打开、引导完成、登录完成、同步成功、记录创建（仅记录类型枚举）、照片添加、提醒启用。服务端对账号 ID 做 HMAC，分析表不保存原始账号 ID；不接受自由文本属性。

**明确禁止上报**：宝宝昵称/生日/性别、照片/文件名/EXIF/object key、奶量/睡眠/排便/身高体重值、疫苗名称日期、备注、手机号、微信标识、账号凭证、token、联系人、定位、剪贴板、广告标识或设备指纹。

### 2026-07-24 的 App Store / 中国大陆发布前缺口

这些是当时的审核前检查项。1.3.4（15）已正式发布，中国大陆 APP 备案已完成；未归档的脱敏运营证据继续补齐，但不再描述为当前发布阻断。

## 10. 技术架构概览

### iOS 侧

| 层 | 主要职责 |
|---|---|
| App Shell | 启动、欢迎引导、四 Tab、导航栈、全局状态与错误提示 |
| SwiftUI Views | 首页、记录中心、喂养、喝水、睡眠、排便、相册、成长、疫苗、月报、纪念日、设置 |
| `BabyRecordStore` | 本地状态、持久化、派生汇总、校验、删除、共享快照 |
| `AppNotificationScheduler` | 喝奶/疫苗等本地通知调度 |
| `FeedingReminderLiveActivityController` | Live Activity 启动、更新、结束 |
| `CloudSyncController` + API Client | 会话、登录、同步/恢复、照片与账号删除 |
| Widget Extension | 只读今日快照和喝奶提醒 Live Activity |
| 资源与设计系统 | 颜色、字体、间距、形状、水彩资产、纸张背景 |

### 后端侧

`Backend/api/server.py` 承载 HTTP 路由，数据库层负责 SQLite/MySQL，存储抽象处理照片对象。后端还包含部署模板、迁移、健康/取证/发布检查和聚合运营看板。它的非目标是“查看每个宝宝的具体内容”。
